# 13. Несколько серверных узлов и PWA

> Статус на 2026-08-11: идентичность узла, реестр подключений, scoped resource
> stores, `/servers`, server-qualified links, optional bearer auth и PWA shell
> реализованы в рабочем дереве. Реальный двухузловой QA, standalone PWA и
> production HTTPS остаются release gates.

## 1. Цель

Пользователь может запустить chat-pi backend на нескольких компьютерах: например,
на рабочем ПК и на VPS. Каждый компьютер является самостоятельным серверным
узлом и может одновременно выполнять свои Chat и Task. Один Web/PWA/Android/iOS
клиент показывает проекты всех добавленных узлов и поддерживает параллельную
работу с ними.

Desktop-вариант остаётся частью общего React Native Web клиента, полноценно
адаптируется под клавиатуру, мышь и широкий экран и устанавливается из браузера
как PWA в отдельном окне.

## 2. Граница серверного узла

Каждый узел самостоятельно хранит и исполняет:

- SQLite/Postgres с Project, Chat, Task, events и очередями;
- канонические checkout и task worktree;
- Pi JSONL-сессии, checkpoints и runtime audit;
- локальные provider credentials, MCP и другие секреты;
- процессы Pi и потоки SSE своих Chat и Task.

Между узлами нет общей базы данных и автоматической миграции активного Chat.
Первый вариант не требует центрального оркестратора: реестр узлов находится в
клиенте, а каждый запрос отправляется прямо на узел-владелец ресурса.

## 3. Идентичность и привязка Chat

Backend имеет стабильный `serverId` (UUID), возвращаемый из
`/api/capabilities` и сохраняемый в `PI_SERVER_ID_FILE` (по умолчанию рядом с
`PI_AGENT_DIR`). Для старых узлов без этого поля клиент использует
детерминированный legacy-идентификатор URL. Для клиента глобальная идентичность
любой сущности — пара:

```text
ResourceRef = { serverId, resourceId }
```

Project, Chat и Task получают `serverId` узла из API-клиента. Chat наследует
`serverId`
от Project при создании; Task, PiSession и event наследуют его от Chat. Перенос
Chat на другой компьютер не происходит неявно и в первую версию не входит.

Это даёт следующие инварианты:

- одинаковые локальные `projectId` или `chatId` на разных узлах не конфликтуют;
- открытый Chat всегда использует API-клиент и realtime-подключение своего узла;
- смена выбранного узла не перенаправляет уже открытый Chat;
- deep link содержит `serverId`, например
  `/servers/:serverId/projects/:projectId/chats/:chatId`; для обратной
  совместимости принимается и query-вариант `?serverId=...`;
- импорт backup на новый независимый узел должен выдать ему новый `serverId`;
  восстановление того же узла сохраняет прежний `serverId`.

## 4. Клиентская модель

Вместо одного `BackendStore.baseUrl` используются:

```text
ConnectionStore
  servers: Map<serverId, ServerConnection>
  activeServerId?: serverId

ServerConnection
  serverId
  name
  baseUrl
  status
  apiVersion
  capabilities
  lastSeenAt
  credentialRef?

ApiClientRegistry
  clients: Map<serverId, ApiClient>

RealtimeRegistry
  hubs: Map<serverId, RealtimeHub>
```

Хранилища Project, Chat и Task индексируются по составному ключу
`serverId:resourceId`. Одновременно могут работать несколько scoped
`RealtimeHub`: потеря связи с одним узлом не останавливает остальные. Подписки освобождаются,
когда для узла нет активных экранов или фоновых задач, с отдельной политикой для
уведомлений о завершении Task.

Сохранённый реестр подключений содержит URL, отображаемое имя и ссылку на
credential. Токены и ключи не должны храниться в обычном Web localStorage.

Для узла можно включить bearer-защиту через `PI_AUTH_TOKEN` или
`PI_AUTH_TOKEN_FILE`. `/health` и `/api/capabilities` остаются публичными для
discovery, `/api/auth/check`, остальные API и SSE требуют `Authorization`.
Native хранит токен в SecureStore, Web — только в памяти вкладки; SSE Web не
кладёт токен в URL. Это node-level защита, а не полноценный пользовательский
login, pairing или rotation устройств.

## 5. Интерфейс

### Серверы

- Экран `/servers` показывает все добавленные компьютеры, доступность, задержку,
  версию API, ID узла и число активных Task.
- Можно добавить, переименовать, переподключить, выбрать и удалить подключение
  из клиента.
  Удаление подключения не удаляет данные на самом компьютере.
- Недоступный узел остаётся в списке и не блокирует работу с доступными.

### Проекты и Chat

- `/projects` агрегирует проекты доступных узлов и явно показывает имя компьютера
  на каждой карточке; недоступный узел не блокирует остальные.
- При потере узла его последний снимок проектов остаётся видимым и помечается
  `offline`; узел, для которого нужен токен, помечается `нужен токен`.
- Новый Project создаётся на явно выбранном узле.
- Новый Chat создаётся внутри Project и поэтому не требует повторного выбора
  узла.
- В заголовке Project и Chat постоянно виден узел-владелец, чтобы пользователь
  понимал, где находятся файлы и исполняется агент.
- Несколько вкладок/окон могут одновременно держать открытыми Chat с разных
  узлов.

## 6. Сеть и безопасность

Для общего доступа с desktop и телефона каждый узел должен иметь стабильный
HTTPS URL, предпочтительно через Tailscale Serve или эквивалентный приватный
reverse proxy. `http://localhost` допустим только для клиента на том же ПК и не
является универсальным адресом узла.

Установленная с HTTPS PWA не должна обращаться к небезопасному HTTP backend:
браузер может заблокировать mixed content и запросы в private network. Поэтому
локальный Windows backend также должен публиковаться через HTTPS. Каждый узел
самостоятельно настраивает CORS allowlist и в будущей публичной конфигурации —
pairing/token authentication с отдельным credential для каждого устройства.

Pi sandbox `bwrap` работает только на Linux. Для Windows-узла до production
нужно выбрать и проверить отдельную изоляцию (например, контейнер/WSL2) либо
явно обозначить ограниченный доверенный режим без `bwrap`.

## 7. Desktop Web и PWA

PWA включает:

- Web App Manifest с названием, иконкой, `display: standalone`, `start_url` и
  корректным `scope`;
- service worker с версионированным кэшем только для app shell и статических
  ресурсов; API и SSE обходят кэш;
- уведомление о новой версии с безопасным обновлением и сохранением draft;
- адаптивные desktop/tablet/mobile layouts, управление мышью и клавиатурой,
  видимые focus states и отсутствие критичных hover-only действий;
- понятный offline-режим отдельно для каждого узла.

Service worker не должен кэшировать изменяющие API-запросы, SSE, секреты и
чувствительные ответы. Offline app shell не означает offline-выполнение Pi:
создание сообщений и Tasks требует доступности их узла. Фоновая работа агента
продолжается на сервере после закрытия PWA.

## 8. Этапы реализации

1. Добавить `serverId` в capabilities и определить составные ссылки на ресурсы.
   **Выполнено.**
2. Заменить одиночный backend store на реестр подключений и мигрировать
   сохранённый `baseUrl` в первую запись реестра.
   **Выполнено.**
3. Создать registry API-клиентов и realtime hubs; квалифицировать кэши Project,
   Chat и Task через `serverId`.
   **Выполнено в клиенте; real two-node QA далее.**
4. Добавить маршруты `/servers`, server selector и агрегированный список
   проектов; перенести deep links на server-qualified схему.
   **Выполнено.**
5. Проверить одновременные SSE/run на двух настоящих узлах и независимое
   восстановление после потери связи.
   **Остаётся release gate.**
6. Добавить manifest, иконки, service worker, update flow и install UI PWA.
   **Выполнено; standalone/installability QA далее.**
7. Провести desktop/tablet/mobile browser QA, установленную PWA QA и native QA
   с двумя узлами.
8. До общего интернет-доступа добавить pairing/token rotation, отзыв устройств
   и безопасное управление credentials. Базовая node-level bearer-проверка уже
   реализована, но не заменяет пользовательскую авторизацию.

## 9. Критерии готовности

- В интерфейсе можно добавить локальный компьютер и VPS; проекты доступных узлов
  видны одновременно и явно подписаны.
- Два Chat на разных узлах имеют независимые scoped SSE-контуры в коде; факт
  одновременного выполнения на двух настоящих узлах ещё требует QA.
- Команда из Chat никогда не уходит на активный в UI, но чужой для Chat узел.
- Перезапуск приложения сохраняет оба подключения и корректную привязку Chat.
- Недоступность одного узла не ломает второй.
- Deep link однозначно восстанавливает узел, Project и Chat либо сообщает, что
  нужное подключение ещё не добавлено.
- Web-клиент подготовлен к установке как PWA и standalone-запуску; факт установки
  в Chromium/Edge ещё не зафиксирован.
- Основные экраны пригодны для работы при desktop, tablet и mobile viewport.
- Обновление service worker не теряет черновик сообщения и не кэширует API/SSE;
  автоматический browser QA этого сценария ещё не выполнен.
- Если узел требует auth, discovery и введение токена должны работать до
  загрузки списка проектов; неверный токен не должен менять active node или
  очищать последний снимок проектов другого узла.
